# Часть 2 практики: правило проекта в OpenSpec

Что сделано
1. В `openspec/config.yaml` добавлен блок `rules` (существующий `context` сохранён, второй `rules` не создавался):
   - `design`: обязательная Mermaid-диаграмма взаимодействия; перечислить покрывающие тесты и назвать файл нового теста;
   - `specs`: в каждом сценарии сначала предусловие `Given:`, затем WHEN и THEN;
   - `tasks`: каждая задача содержит команду или наблюдаемое поведение для проверки.
2. Правило проверено на одном фрагменте (без изменения смысла и границ):
   - «до» — `part2/design-before.md` (раздел Decisions архивированного изменения `add-events-filter`, текст D1–D7 как есть);
   - «после» — `part2/design-after.md` (тот же текст D1–D7 плюс форма, которую требует правило);
   - `part2/design.diff` — unified diff: +23 / −1 строк, из удалённых только старый заголовок фрагмента; тексты решений не менялись.

Как проверялось, что правило реально доходит до агента
```
openspec instructions design --change add-events-groups --json
```
В ответе CLI поле `rules` содержит оба правила `design` дословно, поле `context` — язык артефактов. То есть правило попадает в инструкции, которые получает модель, а не только лежит в конфиге.

Живая проверка правила на новом черновике
`openspec/changes/add-events-groups/design.md` — design, написанный уже под правилом: Mermaid-схема потока данных (CLI → ядро → снапшот → вывод) и раздел «Покрытие тестами» с конкретными файлами. Это черновик: `apply` по нему не запускался (по заданию части 2 изменение останавливается до реализации).

Где правило остаётся
`openspec/config.yaml` в репозитории — действует на все последующие изменения, пока его не изменят.
