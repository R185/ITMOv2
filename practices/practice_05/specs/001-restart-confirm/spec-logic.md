# Спецификация фичи: подтверждение перезапуска по клавише R (только логика)

**Feature Branch**: `001-restart-confirm`

**Created**: 2026-10-29

**Status**: Draft

**Input**: User description: «Подтверждение перезапуска по R: одиночное нажатие не должно
мгновенно сбрасывать партию; нужны данные, алгоритм и границы, тестируемые без SDL».

**Область**: только логика (состояние, правила переходов, контракт данных). Отрисовка
оверлея, шрифты, расположение текста и любые визуальные решения — вне этой спеки.

## Факты о текущем коде (проверено в репозитории)

- `src/ui/sdl_app.cpp:466-470`: `case SDLK_r: game.reset(game.snapshot().seed); paused = false;`
  — одиночное R мгновенно сбрасывает партию. Это поведение фича заменяет.
- `Game::reset(seed)` (`src/core/game.cpp:174-192`) обнуляет поле, bag (`reseed`), `ScoreState`,
  hold, tick, аккумуляторы гравитации/lock delay, флаг game over, очищает события и спавнит
  новую фигуру. То есть сброс уже полный — не хватает только «двухступенчатого» ввода.
- Пауза (`bool paused`) и оверлеи живут только в UI: `handle_event` (строка 451),
  `render_frame` (строка 429). В ядре понятия «пауза» нет.
- Game over тоже не блокирует тики внутри ядра: UI проверяет `game.game_over()` и не двигает
  гравитацию (`sdl_app.cpp:571`), а по game over показывает оверлей с подсказкой «PRESS R».
- Рекорд (`best`) читается/пишется через `tetris::read_highscore` / `write_highscore`
  (`src/ui/highscore.cpp`) и пишется **только** в состоянии game over, один раз за партию
  (флаг `best_recorded`, `sdl_app.cpp:589-600`).
- Сценарии headless-прогона используют токен `R` для движения **вправо** (`Action::Right`,
  `action_from_token`), поэтому фича не может добавлять «R» как токен сценария.
- Тесты — один бинарник `tetris_tests` без SDL (`CMakeLists.txt:46-59`), фреймворк —
  макросы `TEST`, `CHECK`, `CHECK_EQ`, `REQUIRE`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Двойное нажатие R сбрасывает партию (Priority: P1)

Как игрок, я нажимаю R один раз и вижу приглашение «нажмите R ещё раз»; если я нажму R
второй раз в течение двух секунд, партия начинается заново с тем же сидом, а счёт, уровень,
очередь, hold и поле обнуляются.

**Why this priority**: это ядро фичи — без него нет ни защиты от случайного сброса, ни
самого перезапуска; остальные истории только уточняют края.

**Independent Test**: без SDL: собрать компонент подтверждения, подать кадр с нажатием R,
проверить, что партия не изменилась; подать второй кадр с R через 200 мс и проверить, что
пришёл итог «подтверждено», после чего вызвать `Game::reset(seed)` и сравнить снапшот с
`Game(seed)`.

**Acceptance Scenarios**:

1. **Given** идёт партия (не пауза, не game over, на поле есть фигуры, счёт > 0), **When**
   игрок нажимает R один раз, **Then** партия не сбрасывается: поле, счёт, уровень, tick,
   активная фигура, hold и очередь next остаются прежними, а подтверждение переходит в
   состояние «ожидание».
2. **Given** подтверждение в состоянии «ожидание», с момента первого R прошло 200 мс, **When**
   игрок нажимает R второй раз, **Then** приходит итог «подтверждено», и владелец сбрасывает
   партию тем же сидом: поле пустое, счёт 0, строки 0, уровень 1, combo -1, back-to-back выкл.,
   hold пуст, tick 0, game over выкл., активна одна новая фигура.
3. **Given** подтверждение в состоянии «ожидание», **When** игрок ничего не нажимает и
   проходит 1999 мс, **Then** подтверждение всё ещё активно и остаток времени равен 1 мс.
4. **Given** подтверждение в состоянии «ожидание», **When** суммарно проходит ровно 2000 мс,
   **Then** приходит итог «истекло», подтверждение снимается, партия и счёт не меняются.

### User Story 2 - Случайное нажатие R безопасно (Priority: P2)

Как игрок, я задел R случайно: если я продолжаю играть (двигаю, вращаю, роняю фигуру) или
ничего не делаю дольше двух секунд, ничего не сбрасывается, а приглашение исчезает само.

**Why this priority**: защита от потери партии — вторая половина ценности фичи; без неё
двойное нажатие только замедляет сброс.

**Independent Test**: подать R, затем игровое действие — ожидать итог «отменено» и
неизменную партию; отдельно подать R и 2000 мс без ввода — ожидать «истекло».

**Acceptance Scenarios**:

1. **Given** подтверждение в состоянии «ожидание», **When** игрок сдвигает фигуру, вращает,
   делает софт-/хард-дроп или hold, **Then** подтверждение отменяется, партия продолжается с
   учётом этого действия, счёт не сбрасывается.
2. **Given** подтверждение в состоянии «ожидание», **When** проходят только тики гравитации
   (фигура падает сама, игрок ничего не нажимал), **Then** подтверждение **не** отменяется и
   окно продолжает отсчитываться.
3. **Given** подтверждение отменено игровым действием, **When** игрок нажимает R снова,
   **Then** открывается новое окно ожидания (без «штрафного» кулдауна).
4. **Given** подтверждение отменено по таймауту, **When** игрок нажимает R, **Then** сразу
   открывается новое окно ожидания, и партия всё ещё не сброшена.

---

### User Story 3 - После game over перезапуск одним нажатием (Priority: P3)

Как игрок, когда партия уже закончилась, я нажимаю R один раз и сразу начинаю новую: экран
game over сам по себе является подтверждением.

**Why this priority**: сохраняет привычный и безопасный сценарий «проиграл — нажал R»;
подтверждение здесь только мешает и не защищает ничего.

**Independent Test**: довести партию до game over, подать один кадр с R — ожидать итог
«подтверждено» за одно нажатие, без состояния «ожидание».

**Acceptance Scenarios**:

1. **Given** партия в состоянии game over, подтверждение неактивно, **When** игрок нажимает R
   один раз, **Then** сразу приходит итог «подтверждено», партия сбрасывается тем же сидом,
   состояние «ожидание» не возникает.
2. **Given** подтверждение в состоянии «ожидание», **When** партия в этом же кадре переходит в
   game over (фигура заперта сверху), **Then** подтверждение снимается с причиной «game over»,
   а следующее нажатие R сбрасывает партию сразу, без второго подтверждения.
3. **Given** игра только что перезапущена после game over тем же сидом, **When** владелец
   сбрасывает флаг «рекорд уже записан», **Then** новая партия может побить рекорд и записать
   его заново при следующем game over.

---

### User Story 4 - Подтверждение не спорит с паузой (Priority: P4)

Как игрок, я ставлю паузу — приглашение подтверждения исчезает; пока пауза включена, R
ничего не делает; после снятия паузы я нажимаю R дважды, если действительно хочу сброс.

**Why this priority**: пауза — второй модальный оверлей; два одновременных приглашения
противоречат друг другу, а бесплатная «заморозка» окна через паузу — дыра в защите.

**Independent Test**: подать R, затем кадр с флагом «пауза» — ожидать отмену с причиной
«пауза»; в кадре с флагом паузы подать R — ожидать итог «проигнорировано».

**Acceptance Scenarios**:

1. **Given** подтверждение в состоянии «ожидание», **When** игрок ставит паузу, **Then**
   подтверждение отменяется с причиной «пауза», партия не меняется.
2. **Given** пауза включена, **When** игрок нажимает R, **Then** нажатие игнорируется: ни
   сброса, ни окна ожидания.
3. **Given** пауза выключена и подтверждения нет, **When** игрок нажимает R дважды подряд,
   **Then** работает обычный сценарий подтверждения (US-1), пауза не включается и не
   выключается побочно.

---

### User Story 5 - UI получает состояние и итог операций (Priority: P3)

Как разработчик SDL-фронтенда, я хочу из логики получать булев флаг ожидания, остаток
времени и прогресс окна, а также машинно-различимый итог каждого кадра, чтобы рисовать
оверлей и выполнять сброс строго по сигналу логики.

**Why this priority**: без этого контракта UI начнёт сам считать время и принимать решения о
сбросе — поведение разъедется с ядром и перестанет тестироваться.

**Independent Test**: проверить, что после первого R состояние отдаёт «ожидание», остаток
2000 мс и прогресс 1.0; после 500 мс — остаток 1500 мс и прогресс 0.75; итог «подтверждено»
возвращается ровно один раз.

**Acceptance Scenarios**:

1. **Given** подтверждение только что включено, **When** UI читает состояние, **Then** он
   получает: флаг ожидания = истина, остаток 2000 мс, прогресс 1.0, длительность окна 2000 мс.
2. **Given** с момента включения прошло 500 мс, **When** UI читает состояние, **Then** остаток
   1500 мс, прогресс 0.75.
3. **Given** кадр дал итог «подтверждено», **When** UI обрабатывает следующие кадры без новых
   нажатий R, **Then** повторного итога «подтверждено» не приходит — только «нет событий».

---

### Edge Cases

- **E-01 Удержание R (автоповтор SDL)**: **Given** игрок зажал R и SDL присылает повторные
  KEYDOWN с признаком повтора, **When** UI передаёт только нажатия без признака повтора,
  **Then** удержание не подтверждает сброс: окно открывается один раз и истекает, партия цела.
- **E-02 Две R в одном кадре**: **Given** окно уже открыто 300 мс назад, **When** в одном
  кадре пришли два нажатия R, **Then** нажатия сводятся к одному, приходит одно
  «подтверждено» (не два сброса).
- **E-03 Слишком ранняя вторая R**: **Given** окно открыто 20 мс назад, **When** приходит
  повторное R (дубль того же физического нажатия), **Then** итог «проигнорировано», окно
  остаётся открытым и **не** продлевается.
- **E-04 Спам R**: **Given** окно открыто, **When** игрок жмёт R каждые 100 мс, **Then** окно
  не продлевается, R с интервалом ≥ 50 мс подтверждает (второе нажатие = сброс), а не
  бесконечно удерживает приглашение.
- **E-05 Истечение и нажатие в одном кадре**: **Given** окно открыто 1990 мс, **When** в кадре
  пришло 20 мс и нажатие R, **Then** время обрабатывается первым: окно истекает, а нажатие
  открывает **новое** окно; партия не сбрасывается неожиданно.
- **E-06 Долгий системный лаг**: **Given** окно открыто, **When** кадр принёс 5000 мс (окно
  вкладки было свёрнуто), **Then** окно истекает одним шагом, остаток зажимается в 0, партия
  и счёт не трогаются.
- **E-07 Сброс на пустой партии**: **Given** партия только начата (счёт 0, строк 0), **When**
  игрок нажимает R один раз, **Then** подтверждение всё равно требуется — правило не зависит
  от накопленного прогресса.
- **E-08 Game over во время окна**: **Given** окно открыто, **When** в том же кадре партия
  уходит в game over, **Then** окно снимается без ожидания, а нажатие R в этом же кадре
  сбрасывает партию сразу (итог «подтверждено»).

## Requirements *(mandatory)*

### Модель состояния

Компонент хранит ровно два устойчивых состояния: **«покой»** и **«ожидание»**.

```
покой --R (партия идёт)--> ожидание(источник: game)
покой --R (пауза)--> ожидание(источник: pause)
ожидание --R (>= 50 мс, <= 2000 мс)--> подтверждено --> покой
ожидание --2000 мс--> истекло --> покой
ожидание --игровая клавиша (проглатывается)--> отменено (причина: действие игрока) --> покой
ожидание --потеря фокуса--> отменено (причина: focus_lost) --> покой
ожидание --game over--> отменено (причина: game over) --> покой
покой --R (game over)--> подтверждено (сразу) --> покой
```

При открытии из паузы (`источник: pause`) подтверждение снимает паузу и запускает новую партию, отмена оставляет партию на паузе. Пауза при открытом окне невозможна: клавиша P проглатывается как любая игровая клавиша (см. `contract.md`, решение №3).

Длительность окна — **2000 мс**, минимальный интервал между нажатиями —
**50 мс**. Обе границы — часть контракта, а не настройки UI.

### Functional Requirements

- **FR-001**: Логика MUST открывать окно подтверждения на одиночное нажатие R, если нет game over
  и подтверждение ещё не открыто — как при идущей партии (источник `game`), так и при паузе
  (источник `pause`); партия, счёт, поле, очередь next, hold и tick при открытии окна MUST
  оставаться неизменными. *(Согласовано в `contract.md`, решение №1: пауза не блокирует R.)*
- **FR-002**: Окно подтверждения MUST жить ровно 2000 мс, отсчитываемых от кадра, в котором
  пришло нажатие R. Открытие подтверждения MUST NOT обнулять окно при последующих нажатиях.
- **FR-003**: Логика MUST выдавать итог «подтверждено» на нажатие R внутри окна, если с
  момента открытия накоплено не менее 50 мс; при этом партия MUST быть сброшена тем же
  сидом и полностью: поле пустое, счёт 0, строки 0, уровень 1, combo -1, back-to-back выкл.,
  hold пуст, soft/hard-drop счётчики 0, tick 0, game over выкл., активна одна новая фигура.
- **FR-004**: Нажатие R внутри окна ранее 50 мс с момента открытия MUST давать итог
  «проигнорировано» и MUST NOT подтверждать сброс и MUST NOT продлевать или переоткрывать окно.
- **FR-005**: По истечении 2000 мс окно MUST закрываться с итогом «истекло»; партия, счёт,
  поле и рекорд MUST оставаться неизменными.
- **FR-006**: Нажатая при открытом окне игровая клавиша (влево, вправо, три поворота,
  софт-дроп, хард-дроп, hold, пауза) MUST закрывать окно с итогом «отменено» и причиной
  «действие игрока», а само действие MUST NOT применяться к партии — UI проглатывает клавишу и
  передаёт только факт `action_key_pressed`. *(Согласовано в `contract.md`, решение №2.)*
- **FR-007**: Тики гравитации (падение фигуры без участия игрока) MUST NOT отменять окно и
  MUST NOT считаться действием игрока.
- **FR-008**: Пауза MUST NOT включаться, пока окно открыто: клавиша паузы приходит как обычная
  игровая клавиша и проглатывается (FR-006). Окно, открытое из паузы (`source = pause`), при
  отмене MUST оставлять партию на паузе, а при подтверждении MUST снимать паузу и запускать новую
  партию в идущем режиме. *(Согласовано в `contract.md`, решения №1 и №3.)*
- **FR-008a**: Потеря фокуса окном MUST закрывать окно с итогом «отменено» и причиной
  `focus_lost`, не меняя состояние партии. *(Согласовано в `contract.md`, решение №6.)*
- **FR-009**: В состоянии game over подтверждение MUST быть необязательным: одиночное нажатие
  R MUST давать итог «подтверждено» сразу, без открытия окна. Переход партии в game over при
  открытом окне MUST закрывать окно с причиной «game over» и MUST NOT сбрасывать партию.
- **FR-010**: Источник времени — MUST быть реальное прошедшее время, передаваемое снаружи
  целым числом миллисекунд за кадр (один вызов на кадр), а не тики ядра и не внутренние часы:
  тики останавливаются в паузе и при game over, а обращение к системным часам внутри логики
  делает поведение невоспроизводимым в тестах. Внутри логики MUST NOT быть `std::chrono`,
  `SDL_GetTicks`, `time()`, `std::rand` или чтения файлов.
- **FR-011**: UI MUST вызывать единственную операцию «шаг кадра» ровно один раз за
  отрисованный кадр — и в игре, и в паузе, и на экране game over — передавая: прошедшие мс,
  факт нажатия R без автоповтора, флаг паузы, факт game over, факт нажатия игровой клавиши
  (проглоченной, не применённой) и факт потери фокуса окном. Несколько нажатий R в одном кадре
  MUST сводиться UI к одному. Полный список полей входа — раздел 3 `contract.md`.
- **FR-012**: Логика MUST отдавать UI состояние для отрисовки: флаг ожидания (булев),
  остаток времени в мс (целое, 0..2000, 0 при закрытом окне), прогресс окна (вещественное
  0.0..1.0, равен остаток / 2000), длительность окна (2000 мс), источник открытия
  (`game` / `pause`) и причину последнего закрытия окна (нет / подтверждено / действие игрока /
  таймаут / game over / потеря фокуса). Полный список — раздел 2 `contract.md`.
- **FR-013**: Логика MUST возвращать машинно-различимый итог шага из фиксированного набора:
  «нет событий», «окно открыто», «подтверждено», «отменено», «истекло», «проигнорировано».
  Единственный сигнал к сбросу партии — итог «подтверждено»; UI MUST NOT сбрасывать партию ни
  по какому другому признаку и MUST NOT считать таймаут самостоятельно.
- **FR-014**: При нескольких событиях в одном кадре логика MUST разрешать их в порядке:
  (1) время (истечение), (2) переход партии в game over, (3) включение паузы, (4) игровое
  действие, (5) нажатие R. Возвращаемый итог MUST описывать самое позднее из случившихся
  событий; при нажатии R в кадре факт игрового действия в том же кадре MUST NOT блокировать
  обработку нажатия.
- **FR-015**: Итог «подтверждено» MUST выдаваться не более одного раза на окно; последующие
  кадры без новых нажатий MUST давать «нет событий», даже если UI не успел сбросить партию.
- **FR-016**: После закрытия окна по любой причине следующее нажатие R MUST открывать новое
  окно немедленно, без кулдауна; накопленное время предыдущего окна MUST NOT переноситься.
- **FR-017**: Правило подтверждения MUST зависеть только от состояния партии (идёт / пауза /
  game over), а не от набранных очков, числа строк, уровня или «свежести» партии.
- **FR-018**: Рекорд MUST NOT изменяться при открытии, отмене или истечении окна, а также при
  подтверждении в идущей партии: прерванный счёт в файл не пишется, значение рекорда на
  экране остаётся прежним. Перезапуск после game over MUST NOT писать рекорд повторно —
  запись уже произошла при game over; владелец MUST сбросить собственный флаг «рекорд за эту
  партию записан», чтобы новая партия могла записать рекорд снова.
- **FR-019**: Партия после «подтверждено» MUST быть детерминированно равна свежей партии с тем
  же сидом: сериализованный снапшот (включая board-hash и очередь next) совпадает со
  снапшотом только что созданной игры с этим сидом.
- **FR-020**: Модуль подтверждения MUST быть частью ядра: без SDL, без вывода в stdout/stderr,
  без обращений к часам, файлам и глобальному состоянию, собираться в целе `tetris_tests` и
  покрываться юнит-тестами без окна.
- **FR-021**: Фича MUST NOT менять контракт снапшота ядра и JSON для MCP/headless-режима и
  MUST NOT добавлять токен сценария: токен `R` уже означает движение вправо, поэтому состояние
  подтверждения в снапшот игры и в сценарии не попадает.
- **FR-022**: Логика MUST быть устойчива к границам входа: отрицательное или нулевое время
  кадра не двигает окно назад; огромный скачок времени (свёрнутое окно) закрывает окно одним
  шагом; остаток времени MUST зажиматься в 0..2000, прогресс — в 0.0..1.0.
- **FR-023**: Логика MUST NOT выдавать итог «подтверждено» на нажатие R, пришедшее в том же
  кадре, где само окно было открыто (одно нажатие = одно открытие, не самоподтверждение).

### Key Entities

- **Состояние подтверждения**: флаг ожидания (булев), накопленное время с момента открытия
  (мс), причина последнего закрытия. Производные для UI: остаток мс, прогресс 0..1.
- **Вход кадра**: прошедшие мс (целое ≥ 0), нажатие R без автоповтора (булев), пауза
  (булев), game over (булев), применение игрового действия в кадре (булев).
- **Итог шага**: одно из «нет событий», «окно открыто», «подтверждено», «отменено»,
  «истекло», «проигнорировано».
- **Правило фичи**: длительность окна 2000 мс, минимальный интервал 50 мс, приоритет
  game over над подтверждением, пауза блокирует R.

### Граница «ядро / UI»

- **В ядре (тестируется без SDL)**: вся политика — когда открывать окно, когда подтверждать,
  когда отменять, сколько живёт окно, что делать при паузе и game over, какой итог вернуть.
- **В UI**: превращение SDL-событий в факты кадра (фильтр `event.key.repeat`, сведение
  нескольких R в один), передача прошедших мс из уже существующего дельта-счётчика кадра,
  флаг паузы, флаг game over из `game.game_over()`, вызов `Game::reset(seed)` по итогу
  «подтверждено», отрисовка оверлея по состоянию подтверждения, сброс `best_recorded`.
- **Контракт передачи данных в UI** (имена — в терминах контракта, не кода): флаг ожидания,
  остаток мс, прогресс, длительность окна, причина последнего закрытия, итог текущего шага.
  Ничего из этого не обязано попадать в `GameSnapshot` и в JSON снапшота.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100 % одиночных нажатий R в идущей партии не меняют ни одного поля состояния
  игры (счёт, строки, уровень, board-hash, tick, очередь next, hold) — проверяется тестом.
- **SC-002**: Границы окна точны до миллисекунды: при 1999 мс окно ещё активно (остаток 1 мс),
  при 2000 мс закрыто с итогом «истекло» — два отдельных теста, оба зелёные.
- **SC-003**: После «подтверждено» снапшот партии побайтово равен снапшоту `Game(seed)` с тем
  же сидом (включая board-hash) — 1 тест на 3 разных сида.
- **SC-004**: Все правила покрыты юнит-тестами в `tetris_tests` без SDL: не менее 20
  проверяемых сценариев, `make test` зелёный, модуль подтверждения не содержит вхождений
  `SDL`, `chrono`, `GetTicks`, `time(`, `rand` (проверяется поиском по файлу модуля).
- **SC-005**: Удержание R (повторы с признаком повтора) подтверждает сброс в 0 % случаев —
  тест с последовательностью «нажатие + 100 повторов».
- **SC-006**: Одиночное R в состоянии game over сбрасывает партию в 100 % случаев (1 тест), а
  открытое окно при переходе в game over закрывается без сброса (1 тест).
- **SC-007**: Файл рекорда не изменяется ни при открытии, ни при отмене, ни при истечении
  окна, ни при подтверждении идущей партии — тест со временным файлом сравнивает содержимое
  до и после.
- **SC-008**: Headless-симуляция не изменилась: `make sim SEED=42` дважды даёт одинаковый
  board-hash, и ни один существующий тест ядра не отредактирован под фичу.

## Assumptions

- Пауза остаётся состоянием UI-слоя: ядро узнаёт о ней только как о факте во входе кадра.
- Время кадра берётся из уже существующего дельта-счётчика SDL-цикла (разница `SDL_GetTicks`),
  частота 60 кадров/с, время передаётся целыми миллисекундами.
- Перезапуск всегда идёт с тем же сидом, что и текущая партия (`snapshot().seed`) — это
  сохраняет воспроизводимость и совпадает с текущим поведением R.
- Новые клавиши не вводятся: подтверждение — только повторное R.
- Партия, прерванная подтверждённым перезапуском, в статистику и рекорд не попадает.
- Визуальная часть (текст приглашения, полоса прогресса, мигание) — предмет соседней спеки
  UI; здесь фиксируется только набор данных, доступных для отрисовки.

## Ожидания от UI-слоя (для согласования контракта)

1. UI вызывает «шаг кадра» ровно один раз за отрисованный кадр, включая паузу и game over, и
   передаёт полное прошедшее время кадра; своего таймера подтверждения UI не держит.
2. UI сводит SDL-события в факты: нажатие R считается только при `event.key.repeat == 0`,
   несколько нажатий в одном кадре — одно нажатие.
3. UI передаёт флаг паузы и факт game over из ядра игры в каждом кадре; сам решает, ставить ли
   паузу, но не решает, отменять ли окно подтверждения.
4. UI сбрасывает партию только по итогу «подтверждено» и только вызовом `Game::reset` с сидом,
   взятым до сброса; никаких собственных условий «пора перезапустить».
5. UI рисует оверлей по данным логики: флаг ожидания, остаток мс, прогресс 0..1, длительность
   окна; при флаге «ожидание» = ложь оверлей не рисуется.
6. UI сбрасывает свой флаг «рекорд за эту партию записан» при перезапуске и не пишет рекорд при
   подтверждении в идущей партии.
7. UI не добавляет состояние подтверждения в снапшот и JSON и не заводит новых токенов
   сценария (токен `R` занят движением вправо).
