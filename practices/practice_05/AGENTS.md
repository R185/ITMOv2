# AGENTS.md — Tetris (Practice 4, контекст-инжиниринг)

Договор с LLM-агентами, работающими в этой папке. Читается в начале каждой сессии


---

## 1. Продукт

**Идея.** Классический Tetris («Modern Tetris», guideline-совместимый) — десктопная
игра на C++ со SDL2-окном и отдельным headless-режимом, пригодным для детерминированной
симуляции из тестов и MCP-инструментов.

**Почему такой продукт.** Нужен маленький, но по-настоящему тестируемый продукт:
детерминированное ядро (сид → фиксированная последовательность), поэтому любое поведение
воспроизводимо и его можно проверять машинно — из unit-тестов и из MCP-инструментов агента.

**User stories (см. `docs/spec.md`):**
- US-1: как игрок, я хочу сдвигать/вращать фигуру по стандарту SRS и видеть ghost-piece.
- US-2: как игрок, я хочу hold, очередь next из 7-bag, уровни и рост скорости.
- US-3: как игрок, я хочу честный счёт (single/double/triple/tetris, T-spin, combo, back-to-back)
  и рекорд в `~/.local/share/tetris/highscore`.
- US-4: как тестировщик, я хочу детерминированный headless-прогон (`--seed`, скрипт входов),
  который печатает состояние ядра в JSON.
- US-5: как LLM-агент, я хочу получать спеки, прогонять симуляции и рендерить поле
  через MCP-сервер, не читая и не переписывая C++-код.

## 2. Технологический стек

| Слой | Решение | Обоснование |
|---|---|---|
| Язык | C++20 | без внешних зависимостей у ядра, `-std=c++20` |
| Сборка | CMake ≥ 3.20 + `Makefile`-обёртка | `make build/test/run/sim` — требование курса |
| Графика | SDL2 (2.32, системный pkg-config), опционально | окно только для UI; ядро рисуется в ASCII |
| Тесты | ctest + минимальный самописный assert-хедер | нет сети для внешних тест-фреймворков в CI |
| Ввод | сценарный (`--script`) + SDL-события | один и тот же ввод для людей и для агентов |
| MCP | Python 3.13 + официальный SDK `mcp`, transport stdio | прототип MCP практики 4 |
| Скилл | `skills/tetris-cpp/SKILL.md` | проектная процедурная память агента |

**Запрещено:** тянуть в проект новые зависимости без обновления этой таблицы; использовать
`std::rand`; читать/писать сеть во время работы игры.

## 4. Контракт сборки и проверки

```bash
make build     # конфигурация + сборка (cmake -S . -B build && cmake --build build -j)
make test      # ctest --output-on-failure в build/
make sim SEED=42 SCRIPT=LLCWDHD   # headless-прогон, JSON на stdout
make run       # запуск SDL2-окна (нужен дисплей)
make clean
```

**Определение готовности (DoD) любой задачи:**
1. `make build` без ошибок и без новых предупреждений (`-Wall -Wextra`).
2. `make test` — все тесты зелёные, **новое поведение покрыто тестом** (без теста задача не готова).
3. Симуляция с фиксированным `--seed` воспроизводима: два прогона дают одинаковый board-hash.
4. Изменения в поведении отражены в `docs/spec.md`, изменения структуры — в этом файле.
5. Коммит атомарный, сообщение в императиве (`core: add SRS kick table`), без следов генерации
   («as an AI», «sure!», эмодзи в коде и комментариях).

**Definition of Ready:** задача ссылается на US из `docs/spec.md`, имеет acceptance criteria,
не требует новых зависимостей или зависимости уже добавлены в таблицу стека.

## 5. Правила для агента

- **Ядро отделено от UI.** `src/core/*` и `include/tetris/core/*` не знают про SDL и не печатают
  в stdout. Всё, что нужно наружу, отдаётся через структуры/`std::string`.
- **Никакой скрытой случайности.** Случайность только через `PieceBag` с явным `uint64_t seed`
  (xorshift64\*), иначе ломается воспроизводимость и MCP-симуляция.
- **Заголовки — интерфейс.** Реализацию можно менять свободно, сигнатуры в
  `include/tetris/` — только через архитектора (человека), иначе расходится MCP-контракт.
- **Порядок работы:** сначала тест на новое поведение, потом реализация (TDD), потом
  `make test`. Не «потом допишу тесты».
- **Одна задача — один смысл.** Не рефакторить попутно чужой код; заметил проблему — отметь
  в отчёте, не правь.
- **Не выдумывать API.** Прежде чем использовать функцию SDL/std, проверь её в заголовках
  системы (`pkg-config --cflags sdl2`) или в документации, а не по памяти.
- **Часть работы делается агентом, часть — человеком:** решения о структуре, спеках и
  интерфейсах принимает человек; агент реализует, тестирует и отчитывается.
- **Инструменты дороже правды:** если что-то не сходится (тест падает, сборка ломается) —
  сообщать фактический вывод, не «должно работать».

## 6. Как агент использует обвязку практики 4

1. **Скилл** `tetris-cpp` (в этой папке и в `~/.hermes/skills/tetris-cpp/`) — процедуры:
   как добавить фичу, как прогнать симуляцию, типовые грабли ядра.
2. **MCP-сервер** `mcp_server/tetris_mcp.py` — инструменты `info`, `spec`, `sim`,
   `render`, `build`, `test` (в сессии агента видны как `mcp__tetris__sim` и т.д.).
   Регистрация: `hermes mcp add`, см. `mcp_server/README.md`. MCP отдаёт агенту
   *наблюдаемое поведение продукта*, а не код.
3. **Границы ответственности.** MCP-инструменты только читают и запускают; они не меняют
   исходники. Изменения в коде — только через правки файлов агентом с последующим `make test`.

## 7. Хуки проекта (правила, которые исполняются, а не только написаны)

Часть правил из этого файла подключена как shell-хуки Hermes (секция `hooks` в
`~/.hermes/config.yaml`, скрипты — в `hooks/` этой папки):

| Событие | Matcher | Скрипт | Что делает |
|---|---|---|---|
| `pre_tool_call` | `write_file\|patch\|terminal` | `hooks/frozen_headers.py` | блокирует правку `include/tetris/**` — и файловыми инструментами, и через шелл; `fail_closed: true`, то есть упавший гейт не пропускает правку |
| `pre_tool_call` | `terminal` | `hooks/git_gate.py` | уводит `git commit/push/rebase/...` на подтверждение человеком; блокирует команду, если тесты проекта красные |
| `post_tool_call` | `write_file\|patch\|multi_edit\|edit_file` | `hooks/post_edit_check.py` | после правки кода делает инкрементальную сборку и прогоняет тесты; итог кладёт в `build/last_check.json`. Событие наблюдающее, свой ответ вернуть агенту оно не может — результат подкладывает `project_context.py` в следующий ход |
| `pre_llm_call` | — | `hooks/project_context.py` | подкладывает в каждый ход факт: ветка, число незакоммиченных файлов, собрана ли сборка, итог прогона тестов, результат последней автопроверки |

Полезные команды:

```bash
make hooks                                  # hermes hooks list + doctor + самопроверка правил
hermes hooks test pre_tool_call --for-tool write_file   # синтетический выстрел по хукам
HERMES_ALLOW_FROZEN_HEADERS=1 hermes chat   # осознанно разрешить правку интерфейса
```

Границы, о которых надо помнить: гейт ловит файловые инструменты правки и явные признаки
записи в шелле (`>`, `tee`, `sed -i`, `cp`, `mv`, `rm`, `patch`) — экзотический обход он не
поймает; consent на хуки хранится в `~/.hermes/shell-hooks-allowlist.json` и при переносе на
другую машину подтверждается заново (`--accept-hooks` или `hooks_auto_accept: true`).

## 8. Гейты (то, что проверяет ревьювер)

| Гейт | Команда | Ожидание |
|---|---|---|
| Сборка | `make build` | exit 0 |
| Ядро | `make test` | все тесты зелёные |
| Детерминизм | `make sim SEED=42 ...` дважды | одинаковый `board_hash` |
| MCP живой | `hermes mcp test tetris` | сервер отвечает, tools перечислены |
| MCP полезен | вызов `mcp__tetris__sim` из сессии агента | JSON с состоянием игры |
| Хуки здоровы | `make hooks` | все скрипты allowlisted, валидный JSON, правила блокируют |
| Хук срабатывает | правка `include/tetris/**` в сессии агента | вызов заблокирован, причина процитирована |
