# Нагрузочные проверки (CoVe)

Этот документ применяет технику Chain of Verification (CoVe) к исходному файлу нагрузочных проверок. Сначала фиксируем исходные данные, затем даем расширенную спецификацию сценариев и шаги верификации, после чего формализуем артефакты и критерии принятия.

## Исходные данные (из корня)

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| Массовые запросы с малым diff | 50 RPS, 5 минут | Ошибок ≤ 1%, p95 latency ≤ 500 мс без LLM-тупиков | Утилизация CPU, p95/p99 latency, доля таймаутов | Ссылка на отчёт k6/Gatling (CI artifact) |

Если нагрузочное тестирование пока не требуется, обоснуйте это и назовите условие, после которого оно понадобится.

## Расширенная спецификация и верификация

### Сценарий 1: Массовые запросы с малым diff

Цель: проверить устойчивость и задержки сервиса при массовых однотипных запросах с минимальными различиями в полезной нагрузке (малый diff), сфокусировавшись на лимитах API до LLM, чтобы измерение было детерминированным.

Нагрузка и длительность: 50 RPS, 5 минут. Допускается короткий разогрев генератора нагрузки (до 30 секунд) без учета в метриках основного окна.

Допустимые пределы (SLO из исходника): ошибки ≤ 1%, p95 latency ≤ 500 мс, при этом тест выполняется без LLM-тупиков. Под «без LLM-тупиков» понимается изоляция/заглушка вызовов LLM так, чтобы они не влияли на задержки и не вносили недетерминизм.

Что измеряем: утилизация CPU на целевом сервисе/нодах, p95/p99 latency, доля таймаутов.

Инструменты: k6 или Gatling; сбор метрик из APM/экспортеров (например, Prometheus/Grafana), логи сервиса, CI-артефакты.

Процедура выполнения и шаги верификации:
1. Изоляция LLM: включить стабы/моки или флаг, отключающий исходящие запросы к LLM на тестовой среде.
   Проверка: в логах и метриках сервиса за время прогона отсутствуют обращения к LLM-эндпоинтам; конфигурация стаба зафиксирована в артефактах.
2. Подготовка «малого diff»: сформировать набор запросов, в котором полезная нагрузка отличается минимально (например, фиксированный шаблон с малыми вариациями).
   Проверка: приложен пример 10–20 запросов, описан принцип варьирования; зафиксировано, что нагрузка не меняет вычислительную сложность запроса.
3. Конфигурация нагрузки: задать 50 RPS на 5 минут, при необходимости с 10–30 с разогрева.
   Проверка: в отчете генератора зафиксирован фактический RPS и длительность окна; провалов RPS или длительных пауз нет (описать при наличии).
4. Мониторинг ресурсов: включить сбор CPU, latency p95/p99, доли таймаутов.
   Проверка: временные ряды непрерывны на протяжении всего окна; известны интервалы опроса и временная зона; есть привязка к версии билда.
5. Прогон теста: выполнить один контрольный прогон; при флейках выполнить до 3 повторов.
   Проверка: зафиксировать seed/версию скрипта, конфигурацию ГВП (если k6), версию сервиса и деплой.
6. Подсчет метрик: из отчета генератора и мониторинга вычислить ошибки (%), p95/p99 latency, таймауты, нагрузку CPU.
   Проверка: методика и источники указаны; единицы измерения согласованы (мс, %); приложены скриншоты/CSV.
7. Критерии прохождения:
   Проверка: выполнены оба условия — ошибок ≤ 1% и p95 latency ≤ 500 мс. Если одно из условий не выполняется, сценарий считается проваленным; указать доминирующие ошибки и зоны времени деградации.
8. Evidence/артефакты:
   Проверка: в MR/Issue приложена ссылка на CI-артефакт k6/Gatling; приложены графики CPU и latency (p95/p99), лог конфигурации теста, версия сервиса.

Выходные материалы по сценарию:
- Отчет k6/Gatling (линк на CI artifact) с фактическим RPS и метриками.
- Скриншоты/экспорт дашбордов с CPU, latency p95/p99, долей таймаутов за окно теста.
- Краткое заключение Pass/Fail с обоснованием и ссылками на источники метрик.

### Случай, когда нагрузочное тестирование пока не требуется

Требование из исходника: если нагрузочное тестирование пока не требуется, обосновать это и назвать условие, после которого оно понадобится.

Процедура и верификация:
1. Подготовить краткое обоснование (например, отсутствие пользовательского трафика, ранний прототип, отсутствует стабильная среда).
   Проверка: есть явная ссылка на Issue/ADR/архитектурное решение с датой и ответственным.
2. Зафиксировать четкий триггер запуска нагрузочных тестов (например, «после включения фичи X для ≥ N% пользователей» или «после стабилизации API v1»).
   Проверка: условие измеримо и проверяемо; согласовано с командой.
3. Evidence:
   Проверка: ссылка на документ с обоснованием и триггером приложена рядом с тестовым набором (в README/MR/Issue).
