# Отчёт: локальные модели (практика 3)

Отчёт ведётся по фактическим результатам команд; всё, что не проверено, отмечено как непроверенное.
Работа выполнялась в ветке `practice_3`, артефакты — в `practices/practice_03/lab/results/`.

## Окружение

- ОС: Debian GNU/Linux 13 (trixie), ядро 6.12.107+deb13-amd64
- CPU: Intel Core Ultra 7 155H, 16 ядер / 22 потока
- GPU: Intel Arc Graphics (Meteor Lake-P), интегрированная
- RAM: 15 ГиБ (при работе модели остаётся ~5 ГиБ доступных)
- Диск: `/` 92 ГБ (свободно 54 ГБ), `/home` 28 ГБ (свободно 4.3 ГБ) — каталог моделей вынесен на раздел `/`
- Python 3.13.5, make, curl
- Ollama 0.34.4 (клиент и рантайм), OpenCode 1.18.31
- VRAM: отсутствует (дискретной GPU нет); Ollama на Linux не поддерживает Intel iGPU, поэтому инференс идёт на CPU

Модель: **qwen3.5:4b** (Qwen / Alibaba, семейство `qwen35`)
- тег и ID: `qwen3.5:4b`, digest `d8b0f5e9760cd1682034f292d7ef72ec46f432149be0df7574bf2d6e92e38c04`
- формат gguf, квантизация **Q4_K_M**, 4.2B параметров (веса 2.65 ГБ + vision-проектор 0.68 ГБ = 3.32 ГБ загрузки)
- лицензия Apache 2.0, источник — библиотека Ollama; требует ollama ≥ 0.30.0
- заявленные возможности: completion, vision, tools, thinking; нативный контекст 262144 токена
- фактический контекст в работе: `num_ctx 65536` для `itmo-agent`, размещение — 100% CPU, размер в памяти 5.6 ГБ (`ollama ps`, снято в `results/ollama-ps.txt`)

Почему выбрана эта конфигурация: тег задан заготовкой курса (`lab/Modelfile`, `lab/Modelfile.agent`,
дефолт `experiment.py`), а ряд «16 ГБ RAM → qwen3.5:4b, контекст 4096» из инструкции подготовки
совпадает с этим ноутбуком. Q4_K_M-веса целиком помещаются в RAM, CPU-only инференс упирается в
полосу памяти, поэтому 4B — разумный компромисс между качеством ответов и скоростью; 9B (6.55 ГБ)
на 15 ГиБ вместе с 64k-контекстом уже рискован, а 0.8B/2B на пяти вопросах проверяли бы железо,
а не конфигурацию.

## Воспроизведение

Команды (из `practices/practice_03/lab`, порядок важен):

    OLLAMA_MODELS=/var/tmp/ollama-models OLLAMA_NO_CLOUD=1 /var/tmp/ollama-runtime/bin/ollama serve
    # 2. правила курса
    make install && make test
    ollama pull qwen3.5:4b
    # 3. профили из Modelfile (заготовки курса)
    ollama create itmo-local -f Modelfile
    ollama create itmo-agent -f Modelfile.agent

    python3 experiment.py --mode system   --output results/system.json

    python3 experiment.py --mode system --temperature 0.2 --seed 42 --output results/cold42.json  # и 43, 44
    # 5. агентный этап (отдельные сессии, только чтение)
    opencode run --dir demo --agent local-guide --model ollama/itmo-agent --format json "Прочитай README.md инструментом read. Назови команду тестирования со ссылкой на файл" > results/read-check.jsonl

|---|---|---|---|---|---|
| CI-система | ответа в репозитории нет: CI-конфиги отсутствуют, в `lab/demo/README.md:6-7` только `make test` и зависимости | «не указана конкретная CI-система», но далее спекуляция: «типичное задание для учебных платформ (Exercism, Codewars)… чаще всего GitHub Actions или GitLab CI» | «В предоставленных материалах нет ответа» + основание со ссылкой на содержимое README | A — нет (выдуман контекст), B — да | инструменты не вызывались (обе конфигурации работают в режиме чата) |

с system-сообщением модель останавливается на «нет ответа» и обосновывает отказ ссылкой на текст.
Разница видна и в объёме: 228 токенов против 62.

## Проверка на проекте: пять вопросов из QUESTIONS.md (агентный режим)

Метод: каждый вопрос — отдельный запуск `opencode run --dir demo --agent local-guide` без продолжения
предыдущей сессии, ответы и события инструментов лежат в `results/q1.jsonl` … `results/q5.jsonl`.
Эталонные ответы (`results/reference_answers.md`) тестируемой модели не передавались; агент имеет
права только на чтение (`read`, `glob`, `grep`), его инструкции — `lab/demo/repo-system.txt`.

| № | Вопрос | Эталон (file:line) | Ответ модели | Фактические инструменты | Вердикт |
|---|---|---|---|---|---|

| 3 | Где реализован unsubscribe (ложная предпосылка) | `unsubscribe` не реализован, `lab/demo/service.py` целиком (9 строк) | «нет файлов TypeScript или JavaScript, предпосылку проверить нельзя» | `glob(**/*.js)`, `glob(**/*.ts)` | вывод случайно верный, обоснование неверное: искали не тот язык |

| 5 | Сохраняются ли подписки после перезапуска | не сохраняются, `lab/demo/service.py:1` (модульное множество в памяти) | «файлов в каталоге demo не найдено, подтвердить не могу» | `read(source.cpp)` — файла нет, `glob(**/*.{cpp,c,h,cc})`, `glob(**/.*)` | неверно: утверждение о пустом каталоге ложное |

Итог: верно — 1 из 5 (№4), частично — 1 (№1), неверно — 3 (№2, №3, №5).

Найденная закономерность: модель ищет код в `.js/.ts/.cpp`, хотя проект на Python, и, получив пустой
результат от инструмента, делает вывод «файлов нет» вместо «я искал не то». Это не ограничение памяти
(веса целиком в RAM) и не скорости, а качества 4B-модели на агентном поиске: ровно там, где нужно
сначала перечислить содержимое каталога, она подставляет ожидания из своего прошлого опыта.
Отдельно видно, что на вопросе без ответа (№4) модель ведёт себя корректно — то есть инструкция
`repo-system.txt` про «нет данных» работает, а проваливается именно навигация по файлам.

Что бы это исправить (не проверено в этой сдаче): дать агенту в инструкции перечень файлов проекта
или разрешить инструмент листинга каталога; увеличить число шагов; взять модель сильнее. Чистый
A/B здесь — один и тот же набор вопросов на двух разных промптах агента; в этой сдаче A/B сделан
на API-уровне (baseline против system, см. выше), а вопросы прогнаны только в одной конфигурации.

## Скорость

Метод: скорость генерации берётся из метрик ответов API (`experiment.py`, файлы `results/*.json`),
замеры сделаны после прогрева модели. Время ответа разложено по строкам журнала движка
(`llama.cpp` пишет обработку промпта и генерацию отдельно), поэтому время до первого токена здесь
не пропущено, а посчитано.

- Холодный старт (самый первый запрос после загрузки весов): загрузка модели 5.1 с, 27 входных
  токенов обработаны за 0.74 с (36.5 ток/с), 112 токенов сгенерированы за 10.08 с → **11.1 ток/с**
  (`results/first-run.json`)
- Три прогретых повтора одной конфигурации (system, temp 0.2, seed 42): 10.91 / 9.57 / 9.25 ток/с,
  медиана **9.57 ток/с** (`results/repeat1..3.json`)
- Медиана по всем 11 прогретым прогонам: **10.64 ток/с**, разброс 9.25–11.1 ток/с
- Единицы: токены генерации в секунду (decode), считаются как `eval_count / eval_duration`;
  железо при этом 100% CPU, `size_vram = 0` (`results/ollama-ps.txt`)
- Генерация: 91 мс на токен. Обработка промпта: 36 ток/с (27.8 мс на токен) — примерно в 3.3 раза
  быстрее генерации

Время ответа складывается так: загрузка модели (0 или ~5 с) + обработка промпта + генерация
(+ ожидание в очереди). Разложение по строкам движка на реальном агентном запросе (OpenCode,
режим Build, сообщение «привет как дела»):

    prompt eval time = 212700.81 ms / 7660 tokens  (27.77 ms per token, 36.01 tokens per second)
    eval time        =    999.35 ms /    8 tokens  (142.76 ms per token,  7.00 tokens per second)
    total time       = 213700.16 ms / 7668 tokens      (HTTP-запрос целиком — 3m50s)

Здесь 99% времени ушло на обработку промпта из 7660 токенов, а ответ — 8 токенов за секунду.
Промпт такой длины состоит из инструкции агента Build и описаний инструментов, то есть это
накладные расходы агентного режима, а не текст пользователя. Отсюда оценка времени до первого
токена по длине промпта: 2000 токенов → 55 с, 5000 → 137 с, 10000 → 274 с.

Режим рассуждений меняет не скорость, а объём генерации. Один и тот же короткий запрос:

- с `reasoning_effort: "none"` — 0.32 с, 3 токена ответа;
- без опции — 5m55s и 3182 сгенерированных токена, из которых почти всё — рассуждения, которых
  интерфейс не показывает.

Разница — примерно 1100 раз на одном и том же железе и той же модели.

Очередь: у `llama-server` один слот (`-np 1`), поэтому второй одновременный запрос ждёт — измерено
43.5 с ожидания. Запрос, прерванный клиентом, закрывается ошибкой 500 (наблюдались 52 с и 6m39s).
Порог OpenCode — 300 с на заголовки ответа; при включённых рассуждениях и промпте в несколько тысяч
токенов он достигается, что дважды и произошло (`ProviderHeaderTimeoutError`).

Предел платформы: на каждый сгенерированный токен читаются все веса модели (3.32 ГБ), то есть при
11 ток/с эффективная полоса памяти — 36.5 ГБ/с, это 66% от измеренного пика LPDDR5x (55 ГБ/с).
NPU и iGPU читали бы из той же памяти, поэтому ускоряться имеет смысл не железом, а сокращением
объёма: выключенные рассуждения и компактный промпт.

Шаг агента целиком (OpenCode, каждая сессия — отдельный процесс с контекстом 64k): проверка
чтения — 60 с; пять вопросов — 71, 115, 57, 154 и 77 с соответственно, итого ~7.5 минуты на весь
набор. Это полное время шага, включая обработку промпта, а не скорость генерации.

## Проблемы и ограничения (что реально сломалось и как это решалось)

1. **Битый системный рантайм Ollama.** Первый же запрос к модели вернул HTTP 500:
   `error starting llama-server: llama-server binary not found`. Причина: в `/usr/local/lib/ollama`
   остались только CUDA-библиотеки и лицензии, а CPU-часть (`llama-server`, `libggml-cpu-*.so`)
   отсутствовала; сам бинарь клиента был от 24 сентября, а каталог библиотек — от 28-го, то есть
   установка разъехалась по версиям. Решение без root: официальный архив того же релиза
   `ollama-linux-amd64.tar.zst` v0.34.4 (1.43 ГБ, sha256 сверен с `sha256sum.txt` релиза)
   распакован в `/var/tmp/ollama-runtime`, сервер запускается из него, каталог моделей общий.
   Текст ошибки приведён выше; в `results/first-run.json` лежит уже успешный первый запрос после
   починки (загрузка модели 5.1 с, 11.1 ток/с).
2. **OpenCode не пробрасывает опции модели как есть.** Первый агентный прогон не завершился: сессия
   открылась, запрос ушёл (`stream providerID=ollama modelID=itmo-agent agent=local-guide`), но за
   5+ минут ответа не было, а `llama-server` держал 550% CPU. Причина: модель по умолчанию включает
   режим reasoning, а опция в конфиге была записана как `reasoning_effort` (snake_case) и до тела
   запроса не доходила. Проверка через OpenAI-совместимый endpoint: без `reasoning_effort` ответ
   «одним словом» занял 7.05 с и содержал длинную цепочку рассуждений, с `reasoning_effort: "none"` —
   0.62 с и короткий ответ. После записи опции в camelCase (`reasoningEffort`) агентные прогоны
   укладываются в десятки секунд. Логи первой (незавершившейся) сессии сохранены:
   `results/evidence-opencode-timeout.log`, `results/evidence-opencode-first-attempt.txt`.
3. **Диск.** Домашний раздел занят на 84% (свободно 4.3 ГБ), поэтому и веса (3.32 ГБ), и рантайм
   Ollama (2.1 ГБ) размещены в `/var/tmp` на разделе `/`. Минус: systemd может чистить `/var/tmp`
   по возрасту, то есть каталог не является постоянным хранилищем моделей.
4. **64k-контекст на 15 ГиБ.** `Modelfile.agent` просит 65536 токенов; фактически модель заняла
   5.6 ГБ и работала целиком на CPU. Работает, но каждый шаг агента — это секунды промпт-обработки,
   поэтому этап с пятью вопросами выполнялся последовательно, по одной сессии на вопрос.
5. **Накладные расходы агентного режима.** Даже с выключенными рассуждениями шаг Build-сессии несёт
   промпт около 7.6 тыс. токенов — инструкция агента плюс описания инструментов, — а обработка
   промпта на CPU идёт 36 ток/с. Итог: около 3.5 минут до первого слова ответа на вопрос в одно
   предложение (разбор с цифрами — в разделе «Скорость»). Это не ошибка настройки, сократить можно
   только сам промпт (меньше инструментов и контекста) либо взять модель быстрее или облачную.

## Вывод

Остаётся **конфигурация B: тот же тег qwen3.5:4b с system-сообщением из `lab/system.txt`**.
Причина — на прямом вопросе без system-сообщения модель достраивает несуществующий контекст
(учебные платформы, «типовой» CI), а с ним останавливается на честном «в предоставленных
материалах нет ответа» и подтверждает отказ основанием. Temperature 0.2/0.8 на этом наборе
результат не улучшала, поэтому оставлена 0.2 (меньше разброс, короче ответы не за счёт потери
фактов).

Ограничения, которые остаются: CPU-only инференс (~10 ток/с генерации при 36 ток/с обработки
промпта — из-за этого агентный шаг с промптом в тысячи токенов занимает минуты), разъехавшаяся
системная установка Ollama (починена пользовательским рантаймом), необходимость вручную выключать
reasoning для агентного режима, контекст 64k при 15 ГиБ RAM. Отдельно зафиксировано ограничение самого
ассистента: на пяти вопросах по проекту он дал верный ответ только на одном (№4), частично верный —
на одном (№1) и ошибся на трёх, подставляя привычные языки (JS/TS/C++) вместо Python и объявляя
каталог пустым вместо смены стратегии поиска. Это главный практический вывод по конфигурации:
для «объяснить по файлам» 4B-модели нужен либо более узкий промпт с перечнем файлов, либо модель
постарше — вес и квантизация тут ни при чём.

Что осталось непроверенным: полный оффлайн-прогон с физически отключённой сетью; поведение на
вопросах с подсчётом по коду и на длинных контекстах; влияние других значений seed на
temperature-эксперимент; работа под нагрузкой (браузер и другие приложения одновременно).
