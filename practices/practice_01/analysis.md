# Анализ процесса: AS IS и TO BE

## AS IS

Разработчик отправляет в сервис raw-diff через POST /api/reviews. Сервис без валидации и редактирования секретов формирует prompt, синхронно вызывает внешний LLM и возвращает непродуманную структуру ответа {"comment": str}. Узкие места: отсутствие лимита размера входа (API-1), риск утечки секретов в prompt (SEC-1), нет таймаута/обработки ошибок (REL-1), структура ответа не соответствует контракту (OUT-1). Потери информации и нестабильность приводят к ручным доработкам.


## TO BE

Добавить слой валидации входа и редактирования секретов, ограничить размер diff (HTTP 413), вызывать LLM с таймаутом и контролируемой обработкой ошибок, нормализовать ответ в контракт summary/risks/checks.

```mermaid

    A[POST /api/reviews] --> V[Валидация и лимиты]
    V --> R[Редактирование секретов]
    R --> C[Вызов LLM с таймаутом]
    C --> N[Нормализация под OUT-1]
    N --> D[Проверяемый результат]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Секреты | Передаются как есть | Редактируются до [REDACTED] | Отправить тестовый token в diff и проверить prompt |
| Размер входа | Не ограничен | 20 000 символов, иначе 413 | Сгенерировать большой diff и ожидать 413 |
| Таймауты | Нет | 10 секунд + контролируемый ответ | Смоделировать зависание LLM |
| Контракт ответа | {comment} | {summary, risks, checks} | Схемная валидация ответа |
